# saucedust

이미지를 올리면 원본이 어느 게시물인지 찾아 주는 역검색 시스템입니다.
Danbooru를 통째로 수집해 벡터로 바꿔 두고, 질의 이미지의 벡터와 가장 가까운
것을 돌려줍니다. 잘리거나 다시 압축되거나 크기가 바뀐 사본도 찾습니다.

여러 대의 컴퓨터에 노드로 나눠 돌릴 수 있습니다. 중앙 노드 한 대가 결과를
모으고 검색을 받고, 나머지는 수집과 계산만 합니다.

실행 방법은 [RUNNING.md](RUNNING.md)에 있습니다. 이 문서는 무엇이 어떻게
생겼고 왜 그렇게 정했는지를 다룹니다.

## 하는 일과 하지 않는 일

수집한 게시물마다 이렇게 남깁니다.

| 남기는 것 | 어디에 | 왜 |
|---|---|---|
| 벡터 | Qdrant와 PostgreSQL | 검색용. PostgreSQL 쪽은 Qdrant가 날아갔을 때 다시 세우기 위한 사본 |
| pHash, dHash | PostgreSQL | 벡터가 비슷하다고 한 것 중 정말 같은 그림인지 가르는 데 씀 |
| 태그, 등급, 점수, 크기 | PostgreSQL | 결과를 보여주고 걸러 내는 데 씀 |
| 384픽셀 축소본 | 노드의 디스크 | 모델을 바꿨을 때 다시 내려받지 않기 위한 최소 사본 |

원본 이미지는 저장하지 않습니다. 1,000만 장이면 수십 테라바이트입니다.
축소본만 두면 같은 수를 수백 기가바이트로 감당하면서, 모델을 갈아 끼워도
Danbooru를 다시 훑지 않고 벡터만 다시 계산할 수 있습니다.

## 구성

```
                    ┌──────────── 중앙 노드 (control) ────────────┐
  브라우저 ────────▶ │  HTTP API  ·  웹 대시보드  ·  텔레그램 봇   │
  텔레그램 ────────▶ │                                             │
                    │  PostgreSQL   Qdrant   임베딩 워커          │
                    └──────────▲──────────────────────────────────┘
                               │ 벡터와 메타데이터
              ┌────────────────┼────────────────┐
        작업 노드          작업 노드         작업 노드
     (수집 + 계산)      (수집 + 계산)     (수집 + 계산)
              │                │                │
              └────────────────┼────────────────┘
                               ▼
                          Danbooru
```

노드는 PostgreSQL에서 ID 구간을 하나 빌려 그 범위를 수집하고, 끝나면 반납합니다.
빌리는 순간 다른 노드는 같은 구간을 가져갈 수 없으므로 일이 겹치지 않습니다.
노드가 죽으면 심장박동이 끊기고, 중앙 노드가 그 구간을 회수해 다시 내놓습니다.

## 폴더

```
cmd/saucedust/        명령줄 진입점과 조립
internal/domain/      개념과 규칙. 아무것도 의존하지 않음
internal/app/         유스케이스와 포트(인터페이스)
internal/adapter/     포트의 실제 구현
internal/config/      환경값 읽기와 검증
python/worker/        임베딩 워커
scripts/              빌드와 검증
```

의존 방향은 한 방향입니다.

```
cmd  ──▶  adapter  ──▶  app  ──▶  domain
```

`domain`은 PostgreSQL도 HTTP도 모릅니다. 해밍 거리, 벡터 정규화, 어떤 게시물을
건너뛸지 같은 규칙만 있습니다. `app`은 인터페이스만 알고 구현은 모릅니다.
그래서 저장소를 바꾸거나 다른 사이트를 붙일 때 규칙을 건드리지 않아도 되고,
시험할 때 진짜 DB 없이 가짜를 꽂을 수 있습니다.

어댑터는 여덟 개입니다.

| 어댑터 | 하는 일 |
|---|---|
| `postgres` | 이미지, 벡터 사본, 구간 임대, 노드 상태 |
| `qdrant` | 벡터 색인과 근사 최근접 검색 |
| `danbooru` | 게시물 목록과 이미지 내려받기, 속도 제한 |
| `embedworker` | 같은 노드의 Python 워커 호출 |
| `netpath` | 직접, ECH, 조각내기, 프록시 중에서 되는 경로 고르기 |
| `filestore` | 축소본 보관 |
| `httpapi` | HTTP API와 대시보드 |
| `telegram` | 봇 |

## 왜 이렇게 정했는지

### 모델을 두 종류 씁니다

같은 그림 찾기와 비슷한 그림 찾기는 다른 일입니다.

- **copy**: 잘리고 다시 압축된 같은 그림을 찾습니다. 역검색의 본체입니다.
  실측으로 **SigLIP**(768차원)을 골랐습니다.
- **semantic**: 분위기나 구도가 비슷한 다른 그림을 찾습니다.
  **CLIP**(512차원)을 씁니다. 가장 빠르고 가볍습니다.

한 모델로 둘 다 하려면 어느 쪽이든 나빠집니다. 모델마다 Qdrant 컬렉션을
따로 두므로 나중에 하나만 갈아 끼울 수 있습니다.

수집을 크게 시작하기 전에 어느 copy 모델을 쓸지 정해야 합니다. 나중에 바꾸면
쌓인 것을 전부 다시 계산해야 합니다.

### 모델 비교 실측

실제 Danbooru 이미지 6,299장을 받아 후보로 넣고, 그중 1,500장을 다섯 가지로
망가뜨려 검색해서 원본이 1등에 나오는 비율을 쟀습니다. 2026년 8월 2일
측정입니다.

| 망가뜨린 방식 | 지각 해시만 | DINOv2-base | DINOv2-large | **SigLIP** | CLIP |
|---|---|---|---|---|---|
| 절반 축소 | 98.5% | 99.9% | 100.0% | 100.0% | 99.8% |
| JPEG 품질 40 | 98.5% | 99.9% | 99.5% | 99.6% | 99.5% |
| 10퍼센트 잘라냄 | **13.5%** | 97.0% | 96.5% | **98.5%** | 97.7% |
| 워터마크 | 92.7% | 99.5% | 99.7% | 99.4% | 99.7% |
| 화면 촬영 흉내 | 23.3% | 99.0% | 98.5% | 99.0% | 98.4% |
| **전체** | **65.3%** | 99.1% | 98.8% | **99.3%** | 99.0% |
| 처리 속도 | — | 28장/초 | 12장/초 | **32장/초** | 48장/초 |
| 차원 | — | 768 | 1024 | 768 | 512 |

세 가지가 확실해졌습니다.

**해시만으로는 서비스가 안 됩니다.** 잘라낸 그림에서 13.5퍼센트입니다.
해시는 그림 전체를 한 덩어리로 보므로 가장자리가 잘리면 다른 값이 나옵니다.
사람들이 실제로 올리는 것이 대개 잘린 그림이라 이 칸이 중요합니다.

**모델을 키우면 오히려 나빠집니다.** DINOv2-large가 base보다 정확도도 낮고
2.4배 느립니다. 원본 찾기는 그림의 낮은 수준 생김새를 보는 일이라 표현이
추상적일수록 불리한 것으로 보입니다.

**SigLIP이 정확도도 속도도 1위입니다.** 이름은 글과 그림을 맞추는 모델처럼
들리지만 원본 찾기에서 가장 좋았습니다. 차원도 768로 DINOv2와 같아 저장
용량이 늘지 않습니다.

후보 수가 결과를 좌우합니다. 같은 측정을 후보 200장으로 하면 네 모델이
모두 99.8퍼센트를 넘어 우열을 가릴 수 없습니다. 수만 장으로 잡으십시오.

```bash
python/worker/.venv/bin/python python/worker/benchmark.py \
  --images ~/.saucedust/thumbs --limit 20000 --queries 2000
```

`--limit`이 후보 수, `--queries`가 검색해 볼 횟수입니다. 어려움을 정하는
것은 후보 수이고 걸리는 시간을 정하는 것은 검색 횟수입니다.

### 없는 그림을 없다고 말하기

위 측정은 정답이 후보 안에 반드시 있다고 치고 잰 것입니다. 사람들은 아직
수집하지 않은 그림도 올리므로 그때 무슨 일이 벌어지는지도 재봤습니다.
후보에 **없는** 그림 300장을 넣고 1등 점수를 봤습니다.

**벡터 점수만으로는 가릴 수 없습니다.** 진짜와 가짜의 겹침이 DINOv2 64퍼센트,
CLIP 76퍼센트, SigLIP 84퍼센트입니다. SigLIP이 가장 나쁜 이유는 남남에게도
후한 점수를 주기 때문입니다.

**해시로 다시 세우면 갈라집니다.** 5비트 선에서 진짜 43퍼센트를 건지고
가짜는 하나도 통과하지 못합니다. 그리고 이 수치가 세 모델 모두 같습니다.
있고 없음을 가리는 일은 해시가 하고 벡터 모델은 관여하지 않습니다.
그래서 모델은 1등 비율과 속도만 보고 고르면 됩니다.

```bash
python/worker/.venv/bin/python python/worker/threshold.py \
  --images ~/.saucedust/thumbs --gallery 20000 --queries 1000 --rerank 10
```

### 모델을 나중에 바꿀 수 있습니다

축소본을 남겨 두는 이유가 이것입니다. 모델을 바꾸면 쌓인 벡터가 전부
쓸모없어지지만, Danbooru를 다시 훑을 필요는 없습니다.

```bash
saucedust model add -id 새모델 -kind copy -vector-size 768
saucedust reembed -model 새모델 -dry-run
saucedust reembed -model 새모델
```

축소본에서 다시 계산하므로 네트워크를 쓰지 않고 GPU 속도만큼 나갑니다.
다시 내려받으면 28일이지만 이쪽은 며칠이면 끝납니다. 중간에 멈춰도
다음에 부르면 아직 벡터가 없는 것부터 이어서 합니다.

`rebuild`와 다릅니다. `rebuild`는 PostgreSQL에 이미 있는 벡터를 Qdrant로
옮기는 복구용이고, `reembed`는 벡터 자체를 새 모델로 다시 만드는 것입니다.

### 벡터로 좁히고 해시로 가릅니다

벡터 검색은 "비슷한 것"을 잘 찾지만 "같은 것"과 "닮은 것"을 구분하지 못합니다.
그래서 벡터로 후보를 추린 다음 pHash 해밍 거리로 다시 세웁니다.
64비트 기준 5비트 이내면 사실상 같은 그림으로 봅니다.

실측에서 원본을 절반 크기로 줄이고 JPEG 품질 40으로 다시 저장한 사본의
거리가 2였습니다.

### VPN 대신 TLS 인사말을 조각냅니다

한국 회선에서 `danbooru.donmai.us`는 직접 붙지 못합니다. 다만 막는 방식이
TLS 인사말에 적힌 도메인 이름을 보는 것이라, 그 부분이 한 조각에 담기지
않게 나눠 보내면 통과합니다.

2026년 8월 2일 LG유플러스 회선 실측입니다.

| 경로 | 결과 |
|---|---|
| 직접 | 막힘 (연결 끊김) |
| ECH | 못 씀 (서버가 설정을 내놓지 않음) |
| 조각내기 | **통과. 197밀리초, HTTP/2** |
| CDN 직접 | **애초에 안 막힘. 65밀리초** |

이미지 자체는 CDN에서 오는데 CDN은 막혀 있지 않습니다. 막힌 것은 목록을
가져오는 API뿐이고 그것도 조각내기로 통과합니다. **VPN이 필요 없습니다.**
프록시 주소를 넣는 경로는 대비책으로만 남겨 뒀습니다.

### 진짜 병목은 상대 서버의 속도 제한입니다

네트워크도 GPU도 아니었습니다. 동시 요청을 32까지 올리자 429가 쏟아졌습니다.
Danbooru는 IP 단위로 제한하므로 한 노드에서 더 세게 밀어도 소용이 없습니다.
노드를 늘리는 것이 답입니다.

기본값은 초당 5회, 동시 16개입니다. `Retry-After`를 그대로 따릅니다.
계정을 넣으면 한도가 올라갑니다.

### 계산은 GPU 먼저

CUDA, MPS, CPU 순으로 고릅니다. CUDA에서는 fp16을 쓰고 배치를 크게 잡습니다.

준비 단계(디코드와 축소)는 CPU를, 추론은 GPU를 씁니다. 둘을 같은 스레드
묶음에 두면 서로 자리를 뺏으므로 각자의 몫을 정해 뒀습니다. 추론은 짧게
모아 배치로 넘깁니다.

M1 Pro 실측으로 순수 추론 58장/초, 전체 흐름 50~53장/초입니다.

## 얼마나 필요한지

Danbooru 게시물 200장을 실제로 받아 재고, 그 값으로 전체를 계산했습니다.
2026년 8월 2일 기준 최신 게시물 번호는 11,907,690입니다.

측정값입니다.

| | 값 |
|---|---|
| 내려받는 크기 (견본) | 중앙값 119 KB |
| 원본 해상도 (견본) | 중앙값 850x862 |
| 384픽셀 축소본 | 평균 26.7 KB, 95퍼센타일 41.4 KB |
| 준비 시간 (디코드와 축소) | 중앙값 15.0 밀리초 |

전체를 모았을 때 필요한 디스크입니다.

| 무엇 | 용량 |
|---|---|
| 축소본 | 300 GB |
| PostgreSQL 벡터 백업 (모델 2개) | 68 GB |
| Qdrant int8 색인 (모델 2개) | 25 GB |
| PostgreSQL 메타데이터 | 7 GB |
| **합계** | **약 400 GB** |

내려받는 양은 1.4 TB지만 원본을 저장하지 않으므로 디스크에는 남지 않습니다.

수집에 걸리는 시간은 상대 속도 제한이 정합니다.

| | 걸리는 시간 |
|---|---|
| 노드 1대, 초당 5회 | 28일 |
| 노드 3대 | 9일 |
| 노드 5대 | 6일 |
| 노드 10대 | 3일 |

GPU는 초당 58장을 처리할 수 있어 전체를 2.4일이면 끝냅니다. 네트워크가
28일이므로 **GPU는 90퍼센트 넘게 놀고 있습니다.** 속도를 올리고 싶으면
더 좋은 GPU가 아니라 노드를 늘리거나 Danbooru 계정을 넣어야 합니다.

축소본은 게시물 번호로 65,536개 폴더에 나눠 담습니다. 전체를 모아도
폴더당 182개꼴이라 파일 시스템이 느려지지 않습니다.

## 만들고 검증하기

```bash
go build -o saucedust ./cmd/saucedust
```

```bash
./scripts/verify.sh
```

서식, 빌드, `go vet`, staticcheck, gosec, govulncheck, 경합 검사를 켠 Go 시험,
ruff, mypy, Python 시험을 차례로 돌립니다. 저장소나 컨테이너가 필요한 검사는
환경값이 없으면 건너뛰었다고 분명히 알립니다. 조용히 넘어가지 않습니다.

노드에 올릴 실행 파일을 만들려면 이렇게 합니다.

```bash
./scripts/build_nodes.sh
```

macOS와 리눅스, arm64와 amd64 네 가지가 나옵니다. C 의존성을 끄고 만들므로
어느 배포판에나 그대로 올라갑니다.

## 필요한 것

- Go 1.25.5 이상. 그 아래 판에는 표준 라이브러리 취약점이 있습니다
- Python 3.11 이상
- PostgreSQL 16 이상
- Qdrant

준비는 `saucedust setup`이 대신 합니다. 가상 환경을 만들고 torch를 깔고
모델 가중치까지 받아 둡니다. 확인만 하고 싶으면 `saucedust doctor`를 쓰십시오.
